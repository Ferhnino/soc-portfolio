Case studies

Three pieces of SOC work, written up as problem, approach, and result. Details are generalized, and the code is illustrative.

Cutting alert noise in Microsoft Sentinel

The problem

Analysts were manually closing 600+ alerts a week, many of them false positives, which took time away from the alerts that mattered.

The approach

I led a month-long overhaul of the Sentinel analytics: reducing false positives and enriching the detection logic so alerts arrived with the context an analyst needs to decide quickly.

The result

Manual alert closures dropped from 600+ to fewer than 200 a week, a reduction of more than 65% in analyst workload.

Building log ingestion pipelines into Sentinel

The problem

Useful logs arrived as unstructured text or nested JSON, which analysts can't query reliably, and they came from sources with very different network access. Ingestion failures were also hard to spot and slow to diagnose.

The approach

Every new source starts with one question: can it reach the cloud tenant directly? For platforms that can, I configure the integration on both ends: the export on the platform itself, and a Logic App in Azure that either listens for pushed data or polls with a scheduled GET request. For sources that can't, such as isolated or network-gapped servers, Fluent Bit collects the logs locally, pre-parses them with regex, and forwards them through a Data Collection Endpoint to the Data Collection Rule. On either path, a KQL transformation in the DCR shapes the data into structured, queryable tables, and Bash scripts manage log files against disk thresholds.

The result

Both paths end in clean, queryable tables instead of raw text. I also troubleshoot ingestion failures across DCRs, Function Apps, and Fluent Bit feeds, and I've trained SOC engineers on building these pipelines themselves.

KQL that helps analysts investigate faster

The problem

Deep investigations need complex queries, and not every analyst has deep KQL experience. That makes triage slower and the hardest queries harder to share.

The approach

I package complex logic into reusable KQL functions, so an analyst supplies a user and a time window and gets a consistent, readable summary. I also write the heavier queries that sensitive investigations require.

Illustrative example: a reusable user sign-in summary (standard Sentinel SigninLogs schema)

let UserSignInSummary = (user: string, lookback: timespan) {
    SigninLogs
    | where TimeGenerated > ago(lookback)
    | where UserPrincipalName =~ user
    | summarize
        Attempts  = count(),
        Failures  = countif(ResultType != "0"),
        Countries = make_set(tostring(LocationDetails.countryOrRegion)),
        Apps      = make_set(AppDisplayName),
        FirstSeen = min(TimeGenerated),
        LastSeen  = max(TimeGenerated)
      by UserPrincipalName, IPAddress
    | order by Failures desc
};
UserSignInSummary("user@contoso.com", 7d)

Illustrative example: shaping raw JSON into structured columns

RawLogs_CL
| extend p = parse_json(RawData)
| project
    TimeGenerated,
    Host      = tostring(p.host),
    Severity  = tostring(p.severity),
    SourceIP  = tostring(p.src_ip),
    User      = extract(@"user=(\S+)", 1, tostring(p.message)),
    Message   = tostring(p.message)

The result

Analysts with limited KQL experience can investigate effectively, triage is faster, and the team has a shared set of tested queries to build on.

Featured build

threat-feed-lite

A lightweight threat-intelligence aggregator, built to replace a full OpenCTI deployment with something one analyst can actually run and maintain.

The problem

I'd built a full OpenCTI instance — Docker Compose, a VM with 28GB of RAM, a dozen connectors — and it worked, but it was more infrastructure than a single analyst needs for day-to-day intelligence gathering. Standing it up taught me a lot; running it long-term wasn't worth the overhead.

What I built instead

threat-feed-lite runs directly on my desktop — no VM, no web app. It ingests feeds into SQLite with entity and relationship extraction, has a small native Tkinter interface, and connects to Claude Desktop over MCP so I can query and correlate the dataset in plain language instead of hand-writing SQL. Findings get saved as local markdown reports. On top of that, I built a repeatable workflow for Claude to run against the dataset: gather everything relevant to a topic and map how the actors, malware, and techniques connect, tier each finding by recency and confidence, report back before writing anything, and only then populate a formatted hunt report once I've signed off on scope.

Keeping it running

Ingestion is scheduled hourly through Windows Task Scheduler, tuned to skip cleanly if the machine is asleep and catch up on the next run rather than forcing a wake.
